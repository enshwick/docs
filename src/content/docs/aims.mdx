The aim of Enshwick is a framework that does not break when the game updates.

These are the things I would like Enshwick to do next. None of them has a date.
Until version 1.0, any of them may change.

## Will mods keep working across versions?

From version 1.0, I would like the link between Enshwick and a mod to grow only
by additions. A mod built for an older 1.x version would then keep loading
without a rebuild.

Until 1.0, anything may change between alphas. Back up your saves before you
update.

## Which languages will mods use after 1.0?

After version 1.0, I would like mods in more languages, such as Zig, Go, C#,
JavaScript and Python. They would come through WebAssembly. It is the first
thing I plan after 1.0.

Today you write mods in Rust, C, C++ and Luau, or as data with no code. Other
languages that can export C functions work too, but we do not test them.

A WebAssembly mod could come from any language that has WebAssembly tools. Each
language would join when its tools are stable.

A WebAssembly mod would run in a
[sandbox](/explanation/how-mods-work/#is-it-safe), as a Luau mod does. It would
reach the game only through Enshwick. As with Luau, the sandbox would not make
the mod safe.

A C# mod could also be a native mod, as a Rust mod is, with the whole API.

## Will Enshwick run mods written for EML?

After version 1.0, I would like Enshwick to run mods written for EML.

## Which game areas will the API reach after 1.0?

For version 1.0, the API aims to cover every
[area for 1.0](/dev/api-coverage/#which-game-areas-does-the-api-cover) on the
API coverage page. After 1.0, I would like it to reach these areas of the game
too. Today a mod reaches most of them only by the game's own names, without an
API made for them.

The living world:

- **Animals, pets and mounts**: tame, breed, feed and ride animals.
- **Farming and growth**: change how plants grow, and add plants and harvests.
- **Fishing**: change what a player catches and where, and add fish and fishing
  spots.
- **Resource nodes**: change what a node drops and when it comes back, and add
  new kinds of nodes.
- **Water and power**: water sources and drains, and power from waterwheels and
  windmills.

Survival and movement:

- **Survival conditions**: cold, drowning, wetness, hunger, thirst, comfort and
  dangerous areas.
- **Movement and traversal**: tune the glider and the grappling hook, and see
  how a player moves.
- **Camera**: see where a player's camera looks. A mod can already turn the
  camera of the local player.

Building and crafting:

- **Production queues**: the queues of smelters and cooking stations, their
  progress, and a finished batch.
- **Logic, puzzles, doors and traps**: signals, puzzles, locked doors and traps,
  for dungeon and puzzle mods.

Creatures, people and combat:

- **Creature behaviour**: factions, aggression, and how creatures notice
  players.
- **Abilities and spells**: new abilities and spells, and their effects.
- **NPC dialogue**: what survivors and other characters say, new answers, and
  the answer a player picks. A mod can already add panels to the dialogue
  screen.

Looks and sound:

- **Appearance**: character looks, dyes and vanity pieces.
- **Visuals**: models, textures, visual effects and animations.
- **Instruments and songs**: songs, and what a player plays.

Tools for mod authors:

- **World queries**: find the ground, what a line hits, what is near a point,
  and a path between two points.
- **Game systems**: run a mod's own logic before, after or instead of the
  game's, and raise the game's own events.

## Will mod texts get plural forms?

I plan to add plural forms to mod texts, by the Unicode CLDR rules. A language
gets its own forms for one, a few and many, so a line such as "3 items" reads
right in it.

## Will this site come in more languages?

I would like this site in more languages than English and Ukrainian.

## Will a mod reload without a restart while you write it?

I would like mod authors to reload their mod while they develop it, without
restarting the game or the server. It would work for every kind of mod that
Enshwick runs, data packs and WebAssembly mods included.

It would be for development on the author's own test world, not for players or
live servers. Today a changed mod needs a restart of the game or the server.

## Will there be mods for one player only?

Mods that run only on one player's game would be nice to have. Today a mod runs
on the server, or on the server and on every player's game. Mods for one player
would need a new look at how those sides work.

## How can you help?

To ask for an API or share an idea,
[open an issue](https://github.com/enshwick/enshwick/issues/new/choose) on
GitHub. Pull requests are welcome too, and the
[contributing guide](https://github.com/enshwick/enshwick/blob/main/CONTRIBUTING.md)
explains how they work. The [API coverage](/dev/api-coverage/) page shows what
the API reaches today.
