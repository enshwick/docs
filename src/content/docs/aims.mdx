The aim of Enshwick is a framework that does not break when the game updates.

These are the things I would like Enshwick to do next. None of them has a date.
Until version 1.0, any of them may change.

## Will mods keep working across versions?

From version 1.0, I would like the link between Enshwick and a mod to grow only
by additions. A mod built for an older 1.x version would then keep loading
without a rebuild.

Until 1.0, anything may change between alphas. Back up your saves before you
update.

## Will Enshwick run mods written for EML?

After version 1.0, I would like Enshwick to run mods written for EML.

## Will mod texts get plural forms?

I plan to add plural forms to mod texts, by the Unicode CLDR rules. A language
gets its own forms for one, a few and many, so a line such as "3 items" reads
right in it.

## Will this site come in more languages?

I would like this site in more languages than English and Ukrainian.

## Will a mod reload without a restart while you write it?

I would like mod authors to reload their mod while they develop it, without
restarting the game or the server. It would work for every kind of mod that
Enshwick runs, data packs included.

It would be for development on the author's own test world, not for players or
live servers. Today a changed mod needs a restart of the game or the server.

## Will there be mods for one player only?

Mods that run only on one player's game would be nice to have. Today a mod runs
on the server, or on the server and on every player's game. Mods for one player
would need a new look at how those sides work.

## How can you help?

To ask for an API or share an idea,
[open an issue](https://github.com/enshwick/enshwick/issues/new/choose) on
GitHub. Pull requests are welcome too, and the
[contributing guide](https://github.com/enshwick/enshwick/blob/main/CONTRIBUTING.md)
explains how they work. The [API coverage](/dev/api-coverage/) page shows what
the API reaches today.
